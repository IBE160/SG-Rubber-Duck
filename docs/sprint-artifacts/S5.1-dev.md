# S5.1 Development Documentation: Frontend Integration

## Objective
The goal of this story was to connect the frontend UI, specifically the `SimulationPage`, to the live data stream provided by the backend's new simulation orchestrator. This required a significant refactoring to handle real-time state management in a robust and scalable way.

## Implementation Details

A Redux-centric approach was chosen to act as the single source of truth for all real-time simulation data.

### 1. Centralized State Management (`store/simulationSlice.ts`)
- A new, comprehensive Redux slice was created to manage the entire state of a simulation run.
- The `SimulationState` includes:
  - `status`: Tracks the simulation's current lifecycle stage (`idle`, `running`, `completed`, `failed`).
  - `simulationId`: The ID of the current run, used for WebSocket connections.
  - `events`: A log of all raw event objects received from the backend.
  - `currentDay`: The current day in the simulation timeline.
  - `taskStates`: A real-time map of the status and progress of each task.
  - `error`: Any errors that occur during the simulation.
- A key reducer, `receiveWebSocketEvent`, was implemented. It acts as a single entry point for all incoming WebSocket messages, parsing the `event_type` and updating the appropriate part of the state. This centralizes all state mutation logic.

### 2. Refactored WebSocket Service (`services/websocket.ts`)
- The `useWebSocket` hook was heavily simplified.
- Its responsibility for managing local state (`useState`) was removed entirely.
- The hook now accepts the Redux `dispatch` function and its sole job is to:
  1. Establish a WebSocket connection when a `simulationId` is present in the Redux store.
  2. Dispatch the `receiveWebSocketEvent` action for every message it receives.
- This change transformed the hook from a stateful component into a lightweight, pure service for connecting to the backend and feeding data into Redux.

### 3. Refactored Simulation Page (`pages/SimulationPage.tsx`)
- All obsolete logic related to the old client-side `SimulationRunner` was removed.
- All local state (`useState`) for `events`, `isConnected`, and `error` was removed.
- The component now uses the `useAppSelector` hook to subscribe to the `simulationSlice` in the Redux store. All data (`status`, `events`, `currentDay`, etc.) is now sourced directly from this global state.
- The components `KpiDashboard` and `EventLog` now receive their props directly from the Redux-managed state, ensuring they always show the most up-to-date information.

### 4. Updated API Service (`services/api.ts`)
- The file was cleaned up to remove several outdated mock simulation functions.
- The real API functions were implemented:
  - `createSimulationRun`: Makes a `POST` request to create a new simulation run entry in the backend and returns the new `simulationRunId`.
  - `startSimulation`: Makes a `POST` request to the `/simulate` endpoint, passing the `simulationRunId` to trigger the background task on the backend.

## Outcome
The `SimulationPage` is now fully driven by the backend. When a user navigates to the page, it automatically creates a simulation run, starts the backend process, and then listens for the stream of events via the WebSocket. The entire UI is a real-time reflection of the simulation's state as managed by Redux.
