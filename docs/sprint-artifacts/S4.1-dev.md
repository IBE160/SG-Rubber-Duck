# S4.1 Development Documentation: Asynchronous Simulation Orchestrator

## Objective
The goal of this story was to implement the core backend logic for running a project simulation asynchronously. This is the heart of the application's simulation capability, bridging the gap between the existing data models and the real-time frontend.

## Implementation Details

To achieve this, several key components were created and modified:

### 1. Simulation Orchestration Logic (`backend/simulation.py`)
- A new file, `simulation.py`, was created to house the main orchestration logic.
- The primary asynchronous function, `run_simulation_scenario`, was implemented. Its responsibilities include:
    - Setting the simulation status to "running" in the database.
    - Fetching all project tasks and risks.
    - Looping through the simulation day-by-day.
    - Broadcasting real-time events (`day_advanced`, `task_started`, `task_completed`, `risk_triggered`) via the WebSocket manager.
    - Applying risk impacts to task durations.
    - Updating the simulation status to "completed" or "failed" upon finishing.

### 2. Asynchronous Task Handling (FastAPI `BackgroundTasks`)
- To prevent the API from locking up during a long-running simulation, FastAPI's `BackgroundTasks` was used.
- A synchronous wrapper function, `run_simulation_scenario_sync`, was created in `simulation.py`. This function's sole purpose is to create a new `asyncio` event loop in the background thread to safely execute the `run_simulation_scenario` function.

### 3. API Endpoint (`main.py`)
- A new API endpoint, `POST /projects/{project_id}/simulate/`, was added to `main.py`.
- This endpoint adds the `run_simulation_scenario_sync` function to the `BackgroundTasks` queue, passing it the database session factory and necessary IDs.
- It immediately returns a `202 Accepted` status to the client, confirming the simulation has started in the background.

### 4. Code Refactoring (`connection_manager.py`)
- The `ConnectionManager` class, which handles WebSocket connections, was extracted from `main.py` into its own module, `backend/connection_manager.py`.
- This was a critical refactoring step to prevent circular dependencies, as both `main.py` (for the WebSocket endpoint) and `simulation.py` (for broadcasting events) need access to the same connection manager instance.

### 5. Database Helper (`crud.py`)
- A new function, `update_simulation_run_status`, was added to `crud.py`.
- This provides a clean, dedicated interface for the simulation orchestrator to update the status and timestamps of a `SimulationRun` record in the database.

## Outcome
With these changes, the backend now possesses a fully functional, non-blocking simulation engine. It can be triggered via a simple API call, and it communicates its entire progress in real-time through WebSockets, as required for the frontend integration in the next story.
